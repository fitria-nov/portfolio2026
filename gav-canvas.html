GAV SmartProcure: Enterprise Procurement & Inventory Blueprint

Dokumentasi Analisis Sistem, Rekayasa Kebutuhan, dan Cetak Biru Pemodelan Integrasi SAP ERP untuk Transformasi Digital Pengadaan MRO (Maintenance, Repair, and Overhaul).

Proyek: Garuda Aviation (GAV) Group Peran: Lead System Analyst Bahasa: Bahasa Indonesia
Fase 1: Discovery & Initiation

01. Executive Summary

Ringkasan eksekutif proyek digitalisasi sistem pengadaan dan inventaris berbasis SAP ERP.

Latar Belakang Proyek

Operasi maskapai penerbangan menuntut kecepatan tinggi dalam ketersediaan suku cadang. Keterlambatan pengadaan memicu status **Aircraft On Ground (AOG)** yang merugikan hingga ratusan juta rupiah per jam. GAV SmartProcure dibangun untuk menjembatani sistem pengadaan berbasis web yang modern dengan backend SAP ERP core guna mempercepat rantai pasok pengadaan suku cadang secara aman dan real-time.

Target Dampak Utama

70%

Pemangkasan Waktu SLA

Mempersingkat siklus *Purchase Request* hingga *Purchase Order* dari 7 hari menjadi di bawah 2 hari.

02. Business Problem Analysis

Identifikasi masalah utama pada sistem berjalan menggunakan Fishbone Analysis (Akar Penyebab Masalah).

Kategori Masalah Penyebab Utama (Root Cause) Dampak Operasional
Proses Manusia Mekanik menginput PR menggunakan formulir kertas/Excel manual; penandatanganan fisik tertunda akibat kendala mobilitas manager. SLA approval memakan waktu 5-7 hari kerja. Suku cadang kritis terlambat tiba di hanggar.
Integrasi Sistem Data inventaris gudang dicatat manual lalu di-input ulang ke SAP GUI secara berkala (tidak real-time). Terjadi selisih stok (desync) hingga 15% antara fisik dan sistem SAP, menyebabkan pembelian darurat.
Validasi Finansial Pengecekan budget cost center dilakukan secara manual oleh tim Finance melalui laporan berkala. Kebocoran pengeluaran atau pengadaan yang melebihi pagu anggaran triwulan berjalan (over-budget).

03. Stakeholder Analysis

Analisis pemangku kepentingan kunci dan matriks akuntabilitas.

Stakeholder Peran Utama Kebutuhan Sistem Kunci
Mekanik / Pemohon Mengajukan kebutuhan suku cadang untuk pesawat di hanggar. Katalog material berbasis web yang intuitif dan integrasi *Part Number* pesawat yang akurat.
Manager Engineering Melakukan otorisasi teknis dan persetujuan PR. Notifikasi persetujuan instan (WhatsApp/Email) dan otorisasi *one-click* via perangkat mobile.
Finance Officer Memantau dan menyetujui anggaran transaksi. Validasi otomatis *hard-stop* anggaran sebelum PR dapat dikirimkan ke level approval selanjutnya.
Warehouse Staff Menerima barang fisik dan mencocokkannya dengan Purchase Order. Antarmuka pemindaian barcode/QR untuk sinkronisasi otomatis *Goods Receipt* (GR) ke SAP.
Fase 2: Pemetaan Proses Bisnis

04. AS-IS Process (Proses Berjalan)

Visualisasi alur kerja pengadaan material manual sebelum transformasi digital dilakukan.

1

Pengisian Formulir Kertas

Mekanik mengisi formulir PR fisik dan mencari katalog Part Number di buku panduan pesawat.

2

Approval Estafet Fisik

Formulir diserahkan dari meja ke meja untuk meminta tanda tangan basah manager dan tim finance.

3

Input Ulang Data ke SAP

Admin procurement mengetik ulang data formulir kertas ke dalam sistem SAP ECC menggunakan T-code GUI.

05. TO-BE Process (Proses Target)

Visualisasi alur otomatisasi pengadaan digital dengan validasi anggaran terintegrasi.

1

Katalog Web SmartProcure

Mekanik memilih suku cadang dari katalog online terintegrasi SAP Material Master.

2

Validasi Pagu Otomatis

Sistem memanggil REST API SAP untuk memeriksa ketersediaan budget cost center secara real-time.

3

Mobile Approval & Pembuatan PO Instan

Manager menyetujui via Mobile. Sistem langsung memanggil SAP BAPI untuk menerbitkan Purchase Order tanpa entri data ulang manual.

Fase 3: Kebutuhan Sistem (BRD & Specs)

06. Business Requirements (BRD Overview)

Kebutuhan tingkat tinggi bisnis untuk meminimalisasi biaya Aircraft On Ground (AOG).

Tujuan Bisnis Utama: Menghilangkan keterlambatan operasional maskapai dengan memastikan seluruh suku cadang pesawat kritis disetujui dalam waktu 4 jam sejak permintaan diajukan. Proses verifikasi anggaran wajib bersifat *Hard-Stop* (tidak dapat dilanjutkan jika sisa budget kurang).

07. Functional Requirements

Spesifikasi fungsional terperinci yang wajib disediakan oleh pengembang.

ID Kebutuhan Nama Fitur Deskripsi Kebutuhan Fungsional Prioritas
FR-01 SAP Budget Validation Sistem wajib memvalidasi ketersediaan dana pada SAP FI/CO modul secara real-time saat klik tombol 'Submit'. Critical
FR-02 Multi-Level Approval Routing Pelepasan dokumen (approval) harus diarahkan dinamis berdasarkan ambang batas pengeluaran (Threshold) PR. High
FR-03 Barcode GR Receiver Aplikasi mobile warehouse harus dapat memindai QR code material untuk mengirim data GR ke modul SAP MM. Medium

08. Non-Functional Requirements

Aspek non-fungsional sistem seperti performa, keamanan, dan ketersediaan data.

Performance SLA

Response time API sinkronisasi data dari portal ke SAP ERP core maksimal **2.5 detik** per transaksi.

Keamanan Data

Otentikasi menggunakan Single Sign-On (SSO) terintegrasi Azure AD. Seluruh transmisi API menggunakan enkripsi TLS 1.3.

Ketersediaan Sistem

Sistem harus beroperasi penuh dengan ketersediaan (availability) minimum **99.9%** (Downtime maks 8.7 jam per tahun).

09. Acceptance Criteria (Gherkin Scenario)

Skenario penerimaan fitur validasi anggaran menggunakan standar bahasa Gherkin.

Scenario: Submit PR dengan Sisa Anggaran Tidak Mencukupi
  Given Mekanik menginput Purchase Request senilai USD 50,000
  And Cost Center yang dipilih memiliki sisa budget SAP sebesar USD 40,000
  When Mekanik menekan tombol "Submit Purchase Request"
  Then Sistem memunculkan pesan error "Transaksi Dihentikan: Saldo Anggaran Tidak Mencukupi"
  And Status Purchase Request diubah menjadi "Rejected - Insufficient Budget"

20. Exception Flow (Penanganan Masalah)

Strategi mitigasi ketika terjadi kegagalan server integrasi SAP.

Kebijakan Kegagalan API (API Offline Exception):

Apabila REST API SAP mengalami timeout > 5 detik, sistem SmartProcure akan secara otomatis menyimpan PR ke dalam antrean lokal (Local Queue) berstatus "Pending Sync" dan memicu peringatan ke tim System Support via Slack Webhook. Sistem akan mencoba melakukan sync ulang setiap 15 menit.
